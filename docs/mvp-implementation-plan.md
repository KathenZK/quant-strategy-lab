# MVP 实施计划

这份文档把当前阶段的中低频永续合约路线拆成可执行开发顺序，目标是在 `2-4` 周内做出第一条稳定主线策略。

默认边界：

- 只做中低频
- 第一家交易所先做 `Binance USDT-M`
- 先做研究、回测、模拟交易
- 主线策略围绕 `basis / funding / OI`
- `liquidations` 先做事件层和风控层

## 1. MVP 目标

第一版不是“全能平台”，而是满足下面 5 件事：

1. 能稳定刷新主线数据
2. 能生成主线因子和研究报告
3. 能跑一条趋势确认主线回测
4. 能把 `liquidations` 接成事件风险层
5. 能对同一策略重复运行并追溯结果

## 2. 第一版只保留什么

### 数据

- `ohlcv`
- `volume`
- `funding_rates`
- `open_interest`
- `basis_or_premium`
- `liquidations`
- `asset_metadata`

### 策略

- 主策略：趋势确认主线
- 增强层：liquidation 事件风险层
- 第二条策略候选：拥挤度反转

### 交易 universe

第一版建议控制在 `5-15` 个高流动性 USDT 永续：

- `BTC`
- `ETH`
- `SOL`
- 再加少量高流动性主流标的

### 明确延后

- 链上
- 多交易所
- order book
- 高频
- 复杂组合优化
- 实盘直连

## 3. 第一版只实现哪 1 条主策略

第一条主策略必须是：

## 趋势确认主线

核心逻辑：

- 价格趋势成立
- `OI` 同方向增加
- `basis` 同方向扩张
- `funding` 没有过热失真

适合当前阶段的原因：

- 信号最稳定
- 数据最容易拿
- 回测最容易跑顺
- 和中低频永续合约方向盘最匹配

第二阶段才加入：

- liquidation 风险层
- 拥挤度反转

## 4. 2-4 周实施顺序

## 第 1 周：主线数据打通

目标：

- 把 `basis / funding / OI` 进入统一数据湖

必须完成：

- 接入 `basis / premium` 原始来源
- 补齐 `basis_or_premium` 标准化表
- 完善 `funding_rates` 和 `open_interest` 的增量刷新
- 完善 `asset_metadata`
- 建立数据质量检查和缺失统计

交付标准：

- 对任一目标 symbol，可以稳定拉到：
  - `1h OHLCV`
  - funding
  - OI
  - basis / premium
- 标准化层可以被 DuckDB 直接查询

不做：

- liquidation
- 新策略
- 多交易所

## 第 2 周：主线因子与研究报告

目标：

- 围绕主线策略补足因子和评估能力

必须完成：

- 增加主线因子：
  - `oi_change_4h`
  - `oi_change_1d`
  - `oi_zscore_3d`
  - `basis_change_4h`
  - `basis_level_zscore`
  - `funding_zscore_3d`
- 补充研究报告输出
- 做因子相关性与筛选
- 在固定 universe 上跑 IC 与分层收益

交付标准：

- 能对一组 symbol 输出主线因子报告
- 能识别哪些衍生品因子有效，哪些重复度高

不做：

- liquidation 风险层正式上线
- 拥挤度反转策略

## 第 3 周：主线回测与组合规则

目标：

- 让趋势确认主线能形成稳定回测链路

必须完成：

- 策略信号定义
- 调仓频率和持仓周期确定
- 组合规则确定：
  - 等权
  - gross / net exposure 限制
  - 单币权重上限
- 成本模型校准：
  - fee
  - slippage
  - funding cost
- 回测报告验证

交付标准：

- 至少有 1 条可以重复运行的趋势确认主线策略
- 回测结果可追溯到数据版本、因子版本和参数

不做：

- liquidation 主信号
- 实盘

## 第 4 周：liquidation 风险层

目标：

- 把 `liquidations` 接成事件层和风险控制层

必须完成：

- 接入 liquidation 实时流
- 原始事件落盘
- 聚合成 `5m / 15m / 1h`
- 生成事件因子：
  - `liq_spike_zscore`
  - `liq_imbalance`
  - `liq_notional_vs_dollar_volume`
  - `event_cooldown_flag`
- 接入风险控制：
  - 降杠杆
  - 暂停新开仓
  - 风险过滤

交付标准：

- 主线策略可以在极端事件时切换风险状态
- liquidation 数据进入研究报告和模拟交易链路

## 5. 每周都要遵守的范围控制

为了避免项目做散，每周都要检查下面这些边界：

- 不加第二家交易所
- 不加链上
- 不碰高频盘口
- 不引入大量新因子
- 不扩大 universe 太快
- 不提前做 Live broker

## 6. 每个阶段的验收标准

### 阶段 A：主线数据

通过标准：

- `basis / funding / OI` 都有标准化表
- 增量刷新可跑
- 缺失率和刷新状态可见

### 阶段 B：主线研究

通过标准：

- 主线因子能产出稳定报告
- 因子有效性和冗余度能分析

### 阶段 C：主线回测

通过标准：

- 趋势确认主线回测稳定
- 成本、资金费率、风险约束可控

### 阶段 D：liquidation 风险层

通过标准：

- liquidation 原始流被存下
- 聚合特征被产出
- 风险层能影响回测与模拟交易

## 7. 第一版的最小交付物

如果只追求一个最小但完整的版本，最后应该至少交付这些：

- 一份主线数据规范
- 一套主线数据刷新命令
- 一套主线因子
- 一份主线因子研究报告
- 一条趋势确认主线回测
- 一套 liquidation 风险层特征
- 一份带风险层的模拟交易结果

## 8. 明确哪些工作第二版再做

第二版再做：

- 拥挤度反转完整策略
- `OKX` 或第二交易所
- `onchain`
- 更细粒度的盘口和执行优化
- 实盘执行
- 调度与长期在线运行

## 9. 当前推荐的开发优先级

如果现在立刻开始继续开发，建议按下面的顺序推进：

1. `basis_or_premium` 数据表与抓取
2. 主线衍生品因子补齐
3. 趋势确认主线策略规则固定
4. 主线回测指标稳定
5. liquidation 原始流接入
6. liquidation 聚合特征
7. liquidation 风险层接入回测与模拟盘

## 10. 决策原则

如果遇到“这个要不要现在做”的问题，统一按下面的规则判断：

- 是否直接服务第一条主线策略
- 是否直接提高研究结果的可重复性
- 是否直接提升回测和模拟盘的一致性
- 是否会显著扩大系统复杂度

只要第四条答案是“会”，而前面三条不是“强相关”，就延后。
