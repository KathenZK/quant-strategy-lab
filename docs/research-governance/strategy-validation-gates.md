# Strategy Validation Gates / 策略验证门禁

本文件定义本仓库从研究版本推进到 runner / dry-run / live 前需要补齐的验证证据。它服务于现有状态机，不引入新状态；状态词仍以 [strategy-status-glossary.md](strategy-status-glossary.md) 为唯一来源。

本规范是仓库内部工作流说明，不是对外复现规格。门禁报告应沉淀在对应策略家族目录下，core ledger 只保存状态、结论和证据链接，不承载完整实验输出。

## 适用原则

- 门禁用于状态迁移：回测结果再好，也不能跳过 `registered -> audit -> live spec -> dry-run -> live`。
- 阈值是默认口径：默认按本文执行；若因策略频率、样本长度、市场结构或数据可得性需要偏离，报告必须说明原因、替代口径和影响，并在家族 `decision-log.md` 记录。
- 缺数据不是通过：例如相位检验缺少足够细的 K 线数据时，只能记录为未完成 blocker。
- 证据按现有目录落地：Markdown 报告进 `diagnostics/`、`ablations/` 或 `notes/`；脚本进 `scripts/`；需保留的 JSON/CSV/图表进 `artifacts/`；状态迁移结论进 `decision-log.md`；core ledger 放紧凑链接。
- 现有 dry-run 或历史版本不因本文件自动降级；但任何后续升 `live` 或重新 promotion，都应按本文补齐缺口。

## 状态迁移映射

| 迁移 | 需要核验的门禁 | 结果落点 |
| --- | --- | --- |
| `explore -> registered` | 不新增门禁；只固定版本身份、参数和证据链接 | core ledger |
| `registered -> audit` | 门禁 0/1/2/5：超额收益、消融、OOS/CPCV、统计显著性 | ablations / diagnostics / decision log |
| `audit -> live spec` | 门禁 3/4/6/7 + live-executable 审计：MC、压力测试、启动时间、相位、真实下单时序 | diagnostics / live-specs / decision log |
| `live spec -> dry-run` | runner 实现、指标/信号对拍、smoke test、创建 `runner-tracking/` | live-specs / runner-tracking |
| `dry-run -> live` | runner 观察证据、运维风控、重启恢复、missing-bar fail-closed、kill switch | runner-tracking / decision log |

## 门禁 0：超额收益基准

目的：确认策略不是把市场 beta 伪装成 alpha。

默认口径：

- 单标的择时/方向策略：策略收益减去同标的 buy-and-hold。
- 篮子或组合策略：策略收益减去等权持有对应标的篮子。
- 报告超额收益序列、IR 或等价显著性指标、样本窗口、成本假设。

判定：

- 超额收益不显著大于 0 时，不推进 promotion；保留为 `registered / not promoted / not live-ready` 或继续探索。
- 对 market making、套利、纯风险转移等非方向策略，应写明不适用理由和替代基准。

## 门禁 1：消融实验

目的：确认入场、过滤、退出、仓位和风控部件不是噪声拟合或死代码。

默认口径：

- 先从当前实际源码或研究脚本列出部件清单，不拨已删除、未接线或被 binary 忽略的参数。
- 每个消融变体都要验证成交笔数或成交序列确实变化；若与 full 完全一致，先排查是否拨了不存在的旋钮或中性化方向错误。
- 报告每个部件关闭后的 PnL、MDD、胜率、Sharpe、trade count 与 full 的差异。

判定：

- Alpha 或过滤部件应有可解释正贡献。
- 风控部件可以牺牲收益，但必须证明降低尾部风险、回撤、裸仓风险或执行风险。
- 无贡献且无风险解释的部件应删除或记录为重构 blocker。

## 门禁 2：OOS / CPCV

目的：检查策略是否只在单一历史切片或调参窗口上有效。

默认口径：

- 优先使用 CPCV 或滚动 OOS；推荐基线为 `IS 60d + gap 10d + OOS 30d`。
- 样本足够时，组合或滚动窗口应尽量覆盖全区间，目标不少于 30 组。
- 报告每个 OOS 窗口的收益、Sharpe、MDD、trade count、零交易窗口数，以及 OOS 正收益占比。

允许偏离：

- 低频策略、数据历史短或事件型策略可以使用更长 OOS、横截面 OOS、walk-forward 或留后段验证。
- 偏离时必须说明有效独立交易数是否足够；不要因为 30 天窗口内只有极少交易就机械否定或机械通过。

判定：

- OOS 正收益占比接近抛硬币、多个 regime 崩塌、或样本外 trade count 不足以判断时，不推进 promotion。

## 门禁 3：Monte Carlo 稳健性

目的：检查历史路径、交易排列、样本抽样和参数邻域轻微变化后策略是否仍稳定。

默认口径：

- `mc1` K 线扰动：对 OHLCV 做小幅噪声或重采样，观察信号和绩效分布。
- `mc2` 交易重排：打乱交易顺序，检查路径依赖和回撤尾部。
- `mc3` 交易抽样：bootstrap 历史交易，得到 PnL、MDD、胜率、Sharpe 的分位数。
- `mc4` 参数扰动：在冻结参数邻域扫描，判断是高原还是尖峰。

允许偏离：

- 无复利 sizing、无连续亏损停机、无路径依赖的策略，可把 `mc2` 与 `mc3` 合并为交易分布稳健性测试。
- 参数是离散规则或外部约束时，`mc4` 应改为邻近可行规则扰动。

判定：

- 报告分布、分位数和最坏区间；若轻微扰动即大面积转亏或参数只在针尖上有效，不推进 `live spec`。

## 门禁 4：压力测试

目的：确认极端行情和执行异常不会造成裸仓、爆仓或保护单失效。

默认口径：

- 历史极端：覆盖策略可用数据中的暴跌、暴涨、闪崩、流动性骤降、宏观事件或资金费异常日。
- 模拟极端：滑点放大、点差扩大、成交延迟、拒单、断流后恢复、连续同向行情、跳空。
- 报告最大回撤、单笔最大亏损、保护单表现、订单失败处理、是否出现裸仓或仓位不一致。

判定：

- 出现无法解释的裸仓、爆仓风险、保护单无效、断流后继续错误下单时，不推进 `live spec`。

## 门禁 5：统计显著性

目的：避免把多次试验后挑中的单点 Sharpe 当作真实 edge。

默认口径：

- 报告 PSR、DSR、MinTRL 或同等统计显著性指标。
- DSR 的试验次数 `N` 应尽量使用家族历史搜索、参数筛选和候选比较的保守估计。
- 本最小版不强制建立 `trials.csv`；若没有台账，报告必须说明 `N` 的估计依据和不确定性。

判定：

- PSR/DSR 不显著、回测长度低于 MinTRL、或 `N` 无法合理估计时，不把统计显著性视为已通过。

## 门禁 6：启动时间敏感性

目的：检查策略是否过度依赖开始运行的那一根 K 线。

默认口径：

- 在原生 K 线上改变实例起跑时间，统计每个起跑点跑到样本末尾的 PnL、MDD、胜率、Sharpe。
- 默认使用分层抽样覆盖牛、熊、震荡等 regime；准备从 dry-run 推 live 前，优先做逐主周期全扫或足够大的样本。

判定：

- 起跑点之间表现离散过大、部分合理起跑点长期崩塌，说明策略对入场时机过度敏感，不推进下一阶段。

## 门禁 7：相位 / K 线切分边界

目的：检查策略是否只在交易所原生 K 线边界上好看。

默认口径：

- 对策略用到的主周期和相关周期逐周期扫描；一次只扰动一个周期，其余周期保持原生。
- 15m 周期优先用 1m K 线重聚合出 `{0, 3, 5, 6, 9, 10, 12}` 分钟相位。
- 1h 及以上周期优先扫描 `{0, 30}` 分钟相位。
- 每个相位抽样多个起跑点，覆盖不同 regime；样本足够时目标不少于 20 个起跑点。
- 聚合必须来自真实更细粒度 K 线或逐笔数据，不能从原生 15m K 线插值伪造偏移 15m。

默认判定：

- 各相位收益中位数应大于 0。
- 非原生相位收益中位数默认不低于原生相位的 60%。
- 非原生相位 MDD 中位数默认不超过原生相位的 1.5 倍。
- 跨相位收益中位数 CV 默认低于 0.5。

例外：

- 若策略明确捕捉原生收线边界订单流或结算节奏，可按“时钟边界 alpha”举证：原生边界附近存在事件效应、信号只在收线后确认、跨月份/年份有效、临近伪边界不等效、扣成本后仍有优势。
- 举证不全时，相位崩塌应视为 `not live-ready` blocker。

## 报告最小模板

每份门禁报告至少包含：

- 策略家族、版本、状态迁移目标。
- 数据来源、市场、symbol、timeframe、UTC 区间、成本模型和 closed-bar 口径。
- 本次覆盖的门禁、默认口径、是否偏离、偏离原因。
- 关键指标、分布或切片结果。
- 通过 / 未通过 / 数据不足的结论。
- 后续状态建议：停留 `registered`、进入 `audit`、进入 `live spec`、或保持 `not promoted / not live-ready`。
- 证据链接：脚本、artifacts、相关 core ledger 和 decision log。
